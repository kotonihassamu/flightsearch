# 運用手順

手動テストの手順は [`テスト手順.md`](テスト手順.md) を参照。

## 日常運用

平常時は何もしない。Bランク以上の便がある日だけ LINE に通知が届く。
0件の日は通知しない仕様のため、「通知が来ない = 正常」である。

## 障害の見分け方

| 症状 | 判断 | 対応 |
|---|---|---|
| 通知が来ない | 正常（該当便なし）の可能性が高い | Actions のログで `run_no_deal` を確認 |
| 「取得失敗」通知が届く | 全路線失敗 | 下記「取得失敗が続く場合」へ |
| Actions が赤い | テスト失敗 or 実行時例外 | ログを確認 |
| 通知の除外件数が急増 | パーサの故障 | フィクスチャテストを実行して切り分け |

サイレント障害（何も起きていないのに何も通知されない状態）を防ぐため、
全路線失敗時は必ず通知が飛ぶ設計になっている（要件4.3）。
逆に言えば、**「取得失敗」通知が届かないのに何日も無通知が続く場合は、
通知経路そのものを疑う**こと。月1回程度 `workflow_dispatch` で手動実行して疎通を確認するとよい。

## 取得失敗が続く場合（要件4.1 の切替基準）

**全路線の取得失敗が3日連続** したら、Bot判定によるIPブロックとみなしローカル実行へ切り替える。

### 切替手順

1. GitHub Actions のスケジュールを止める

   `.github/workflows/daily.yml` の `schedule` セクションをコメントアウトして push。
   （`workflow_dispatch` は残しておくと、後で疎通確認に使える）

2. ローカル環境を用意する

   ```bash
   git clone <リポジトリ>
   cd flight-deal-notifier
   python -m venv .venv
   .venv\Scripts\activate          # Windows
   pip install -r requirements.txt
   copy .env.example .env           # 値を記入
   ```

3. 手動実行して成功を確認する

   ```bash
   set PYTHONPATH=src
   python -m flightdeal.main
   ```

4. スケジュール登録する

   **Windows タスクスケジューラ**

   - 操作: プログラムの開始
   - プログラム: `C:\path\to\flight-deal-notifier\.venv\Scripts\python.exe`
   - 引数: `-m flightdeal.main`
   - 開始（作業フォルダ）: `C:\path\to\flight-deal-notifier`
   - トリガー: 毎日 8:00
   - 「タスクを実行するためにスリープを解除する」にチェック

   環境変数はタスクスケジューラから渡しにくいため、`.env` を読むか、
   バッチファイルでラップする方法を推奨。

   **Raspberry Pi / Linux の cron**

   ```cron
   0 8 * * * cd /home/pi/flight-deal-notifier && \
     /home/pi/flight-deal-notifier/.venv/bin/python -m flightdeal.main \
     >> /home/pi/flightdeal.log 2>&1
   ```

   `PYTHONPATH=src` と `.env` の読み込みを忘れないこと。

5. 1週間ローカルで安定稼働したら、GitHub Actions への復帰は当面見送る

### 切り替えても直らない場合

IPブロック以外の原因（ライブラリの仕様変更、Google Flights の構造変化）を疑う。

```bash
python scripts/phase0_check.py --dest HIJ
```

これが失敗するなら取得方式そのものの故障。要件3.2.2 の優先度2（Playwright）への
切替を検討する。ローカルなら Bot 判定を受けにくいぶん、Playwright の成功率は上がる。

## 設定の見直し

### 相場（market_price）がずれてきたら

Sランクが毎日出る → 相場が高すぎる。実勢の往復相場に下げる。
何ヶ月も通知が来ない → 相場が低すぎる、または max_price が厳しすぎる。

相場は季節変動するため、四半期に一度は見直すとよい。
自動算出は将来拡張（要件7）。

### 路線を追加したいとき

`config.json` の `destinations` に1件足して `enabled: true` にするだけ。
ただし検索回数の上限に注意。

```
有効路線数 × weekends_ahead × 2 ≤ search.max_searches_per_run（既定20）
```

これを超えると起動時に `ValueError` で止まる（要件4.3 の負荷抑制を設定側で強制している）。
路線を増やしたい場合は `weekends_ahead` を1に戻すか、上限値を見直すこと。
ただし上限を上げるほど Bot 判定リスクと実行時間が増える点は要件P4 のとおり。

### 通知の文字数に注意（Phase 3 で顕在化）

全5路線・2週末・各3件を通知すると、本文はおよそ **7,000文字＝LINE 2通**になる。
`LineNotifier` は無料枠に配慮して1実行あたり2通までしか送らないため（要件R6）、
これ以上増えると末尾が切り捨てられる（`line_truncated` がログに出る）。

対策は `notify_top_n_per_route` を 3 → 2 に下げること。
`tests/test_pipeline.py::test_phase3_notification_fits_in_two_messages` が
この上限を監視しているので、通知フォーマットを変更したらテストを回すこと。

## セキュリティ（要件4.4）

- `.env` は絶対にコミットしない（`.gitignore` 済み）
- リポジトリは private にする
- ログにトークン・userId を出さない。ログ出力を追加する際は必ず確認する
- チャネルアクセストークンが漏れた疑いがあれば、LINE Developers で即座に再発行する
