# アーキテクチャ

## 全体の流れ

```
main.py
  │
  ├─ config.load_config()            config.json 読み込み＋検証
  ├─ fetchers.build_fetcher(name)    取得器を生成（stub / fast_flights / fixture）
  │
  └─ pipeline.run(fetcher, cfg)
        │
        ├─ weekend.target_weekends()          対象の土日を決める
        │
        └─ 路線 × 週末 ごとに process_route()   ← try/except で隔離
              ├─ fetch_with_retry(HND → 目的地, 土)    リトライ最大2回
              ├─ sleep_between_searches()               5〜15秒ランダム
              ├─ fetch_with_retry(目的地 → HND, 日)
              ├─ filters.filter_outbound() / filter_return()
              ├─ filters.combine()                      往路×復路 総当たり
              ├─ pricing.effective_price()              手荷物補正＋合算
              ├─ ranking.judge_rank()                   S / A / B / ランク外
              └─ ranking.top_n_per_route()              安い順に上位3件
        │
        └─ RunResult
              │
              ├─ all_failed  → formatter.format_failure() → 障害通知
              ├─ 0件         → 通知しない
              └─ 1件以上      → formatter.format_run() → notifiers.send()
```

## レイヤーと依存の向き

```
        main
          ↓
       pipeline
     ↙    ↓    ↘
fetchers  純粋関数群   notifiers
   ↓    (weekend/filters/     ↓
 base    pricing/ranking)   base
         formatter
          ↓
        models ← config
```

- **依存は必ず上から下へ**。`models` は誰にも依存しない。純粋関数群は `models` と `config` のみに依存する
- `fetchers` と `notifiers` は抽象基底クラスを持ち、`pipeline` は具象実装を知らない

## なぜこの分け方か

**純粋関数群（weekend / filters / pricing / ranking / formatter）**
外部I/Oを一切持たない。入力を与えれば必ず同じ結果が返る。
これにより要件6.1の単体テストが外部サイトの状態に左右されず、CIで安定して回る。
ロジックの誤りはここで全部捕まえる、という設計。

**fetchers**
外部サイトに触る唯一の場所。ここだけが壊れやすいと分かっていれば、
壊れたときの調査範囲が限定される。要件R1の「将来の公式APIへの移行余地」も、
このディレクトリの中身を差し替えるだけで済む。

**pipeline**
「壊れやすい取得」と「壊れない計算」をつなぐ場所。したがって
リトライ・待機・例外の隔離といった防御はすべてここに集約する。
純粋関数の側に try/except を書き始めたら設計が崩れているサイン。

## 交換可能なポイント

| 差し替え対象 | 変更箇所 | 上位への影響 |
|---|---|---|
| 取得方式（fast-flights → Playwright → 公式API） | `fetchers/` に実装追加＋`build_fetcher` に登録 | なし |
| 通知先（LINE → 他のメッセンジャー） | `notifiers/` に実装追加＋`build_notifier` に登録 | なし |
| 実行環境（GitHub Actions → ローカルcron） | 環境変数の与え方のみ | なし |
| 対象路線・週末数・閾値 | `config.json` | なし |

要件4.1「実装は環境非依存とする」は、この表の3行目が守られていることで担保される。
OS依存の処理を書かない、秘匿情報は環境変数からのみ読む、という2点を維持すること。

## 設計上の落とし穴

**ランク判定の丸め** — `market_price * 0.70` は float になる。
35,000 × 0.7 = 24,499.999... のような誤差で境界値テストが落ちうる。
`int(market_price * threshold)` で切り捨ててから比較する方針を推奨（`ranking.py` の docstring 参照）。

**組み合わせ件数** — 往路10便 × 復路10便 = 100通り。時間帯フィルターを先に適用してから
組み合わせること。順序を間違えると無駄な計算が増える。

**除外件数のログ** — 取得項目が欠けた便を黙って捨てると、パーサが壊れたことに気づけない。
除外件数は `RouteResult.excluded_count` に集計され `route_done` ログに出る（要件3.2.2）。
除外率が急に上がったら取得方式の故障を疑う。**全件除外は失敗として扱う**
（`FetchError`）——0件を黙って返すとサイレント障害になるため。

**障害の証拠を残す** — 解析に失敗したときの生HTMLは `artifacts/` に保存される
（`artifacts.py`）。GitHub Actions では失敗時にこれをアーティファクトとして
7日間回収する。これが無いと「あのとき何が返ってきたか」を永久に追えない。
保存自体の失敗は握りつぶす（best-effort）。調査用の仕組みが本処理を止めては本末転倒。

**検索リンクは計算と一致させる** — 本文は「片道×2の合算」なので、リンクも片道検索
（`search_link.py` の tfs URL）を指す。自然言語クエリ（`?q=...`）はGoogleが復路日を
勝手に補完し、本文と全く違う往復価格を表示してしまう（Phase 0 で実際に踏んだ）。
