# 手動テスト手順

自分の手で動作を確認するための手順書。上から順に進める。
**T1〜T7 は外部サイトにもLINEにも一切接続しない**ので、何度でも安全に試せる。
T8以降が実接続を伴うテスト。

> **Windows / PowerShell でコマンドを1つずつ知りたい場合は
> [`PowerShell実行手順.md`](PowerShell実行手順.md) を見てください。**
> こちらは「何をどう確認するか」を説明した文書です。

前提: このフォルダで作業する。

```bat
cd "C:\Users\nuram\OneDrive - 元富士製作所\フライト検索システム"
```

## T0. 環境を準備する（初回のみ）

```bat
python --version
```
→ `3.11` 以上であること。それ未満なら python.org から入れ直す。

```bat
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
```

プロンプトの先頭に `(.venv)` が付いていればOK。
**以降のコマンドはすべてこの `(.venv)` が付いた状態で実行する。**

CLIを直接叩くときだけ、これが必要:

```bat
set PYTHONPATH=src
```

PowerShell の場合は `$env:PYTHONPATH="src"`。
（`pytest` には不要。`pytest.ini` で設定済み）

> `pip install` で fast-flights が入らない場合は、いったん `requirements.txt` の
> `fast-flights` の行を `#` でコメントアウトして進める。
> T1〜T7 は fast-flights なしで全部通る。

## T1. 自動テストが全部通ることを確認する

```bat
pytest
```

**期待する結果**: `129 passed, 3 skipped` と表示される。

> skipped の3件は「実HTMLを使ったパーサ回帰テスト」。まだHTMLを採取していないため
> スキップされる（T8 で採取すると有効になる）。

失敗した場合は、失敗したテスト名がそのまま原因の場所を指している。

| 落ちたテスト | 疑うところ |
|---|---|
| `test_config` | `config.json` を編集して壊した |
| `test_weekend` | 週末算出。日付を跨いだ環境依存 |
| `test_pricing` / `test_ranking` | 判定ロジック |
| `test_pipeline` | 全体の流れ、隔離・リトライ |
| `test_formatter` | 通知本文のフォーマット |

もっと詳しく見たいとき:

```bat
pytest -v                          対象を1件ずつ表示
pytest tests/test_ranking.py -v    ファイルを指定
pytest -k boundary -v              名前に boundary を含むものだけ
```

## T2. ドライランで通知本文を目で見る

**これが一番大事なテスト。** 外部接続なしで、検索から通知本文の組み立てまで通す。

```bat
set PYTHONPATH=src
python -m flightdeal.main --dry-run
```

**期待する結果**: JSONのログが数行流れたあと、`[DRY-RUN] 通知本文` に続いて
広島・松山の便が6件表示される。

### 見るべきポイント

- [ ] 往路の**到着**時刻がすべて 11:00 以前か
- [ ] 復路の**出発**時刻がすべて 17:00 以降か
- [ ] 実質価格 ＝ 往路価格＋復路価格＋補正 になっているか（電卓で1件検算）
- [ ] Jetstar が入っている便に `手荷物 +￥3,500` が付いているか
- [ ] ANA/JAL だけの便は `補正: なし（FSC）` か
- [ ] 割引率（▲◯%）が相場と実質価格から見て妥当か
- [ ] 1路線あたり最大3件までか

ログの `route_done` 行も確認する:

```
"fetched": {"outbound": 3, "inbound": 3},        取得できた便数
"after_time_filter": {"outbound": 2, "inbound": 2},  時間帯で絞った後
"combinations": 4,                               組み合わせ総数
"notifiable": 3                                  通知対象（上位3件）
```

`after_time_filter` が 0 になっている路線があれば、時間帯の条件が厳しすぎる。

## T3. 日付を変えて週末算出を確認する

`--today` で「今日」を偽装できる。実際に土曜まで待つ必要はない。

```bat
python -m flightdeal.main --dry-run --today 2026-07-27
python -m flightdeal.main --dry-run --today 2026-07-31
python -m flightdeal.main --dry-run --today 2026-08-01
python -m flightdeal.main --dry-run --today 2026-08-02
```

ログ先頭の `"date"` を見て、下表のとおりになっていることを確認する。

| 指定した日 | 曜日 | 期待する土曜 | 期待する日曜 |
|---|---|---|---|
| 2026-07-27 | 月 | 2026-08-01 | 2026-08-02 |
| 2026-07-31 | 金 | 2026-08-01 | 2026-08-02 |
| **2026-08-01** | **土** | **2026-08-08** | **2026-08-09** |
| 2026-08-02 | 日 | 2026-08-08 | 2026-08-09 |

**土曜のケースが要注意**。当日を含めず翌週になるのが仕様（要件3.1）。

## T4. 設定を変えて判定が動くことを確認する

`config.json` をいじって、期待どおりに結果が変わるかを見る。
**確認が終わったら必ず元に戻すこと。**

### 4-1. 相場を下げるとランクが落ちる

広島の `market_price` を `35000` → `24000` に変更して実行。

期待: さっきSランクだった￥22,800が **Bランクに落ちる**。
（Sの閾値は 24000×0.7＝16,800、Aは 24000×0.85＝20,400。どちらも超えるが、
相場24,000未満かつ max_price 30,000以下なのでBに該当する）

さらに `max_price` を `30000` → `22000` にすると、Bの条件も外れて
**何も通知されなくなる**（ログに `run_no_deal` が出る）。これも正常な動作。

### 4-2. 時間帯を緩めると件数が増える

`time_filter.outbound_arrive_by` を `"11:00"` → `"14:00"` に変更。

期待: 広島の `after_time_filter.outbound` が 2 → 3 に増える
（12:10発→13:35着の便が通るようになる）。

### 4-3. 手荷物補正を変える

`baggage_surcharge_oneway` を `3500` → `0` に変更。

期待: 松山（Jetstar）の実質価格が￥21,300 → ￥14,300 に下がり、補正表示が消える。

### 4-4. 設定ミスは起動時に弾かれる

わざと壊してみる。`rank_thresholds` を `{"S": 0.90, "A": 0.85}` にして実行。

期待: **検索を始める前に**、以下のように止まる（終了コード2）。

```
設定ファイルに問題があります: rank_thresholds は 0 < S < A < 1 である必要があります (S=0.9, A=0.85)
config.json を確認してください（docs/テスト手順.md T4-4 参照）。
```

同様に、`destinations` を全部 `enabled: true` にして `weekends_ahead` を `2` にすると
20検索ちょうどで通るが、`weekends_ahead` を `3` にすると
`ValueError: 検索回数が上限を超えます` で止まる（要件4.3）。

## T6. 障害時の挙動を確認する

`--fail-route` で、指定した区間だけわざと失敗させられる。

### 6-1. 1路線だけ失敗 → 他は生き残る（要件4.3 路線単位の隔離）

```bat
python -m flightdeal.main --dry-run --fail-route HND-HIJ
```

期待:
- 広島が `route_failed` になる
- **松山の結果はそのまま通知される**
- `pipeline_done` が `"failed": 1, "notifiable": 3`
- 終了コードは 0

### 6-2. 全路線失敗 → 障害通知が出る（要件4.3 サイレント障害防止）

```bat
python -m flightdeal.main --dry-run --fail-route HND-HIJ --fail-route HND-MYJ
```

期待:
- `【取得失敗】航空券を取得できませんでした（全路線）` という本文が出る
- 失敗した路線名と、ローカル実行への切替を促す文が入っている
- 終了コードが **2**（PowerShell は `$LASTEXITCODE`、コマンドプロンプトは `echo %ERRORLEVEL%` で確認。GitHub Actions が赤くなる条件）

### 6-3. リトライしていることを確認

6-2 のログで、同じ区間について `fetch_failed` が `attempt: 1, 2, 3` と
3回出ていることを確認する（初回＋リトライ2回。要件4.3）。

## T7. 通知の分割を確認する

Phase 3 の最大構成では本文が約7,000文字になり、LINEの上限5,000文字を超えて
2通に分割される。T5 の状態で以下を実行:

```bat
python -c "import sys;sys.path.insert(0,'src');from dataclasses import replace;from datetime import date;from flightdeal.config import load_config;from flightdeal.fetchers.stub import StubFetcher;from flightdeal import pipeline,formatter;c=load_config();c=replace(c,search=replace(c.search,sleep_between_searches=(0,0)));r=pipeline.run(StubFetcher(),c,today=date(2026,7,27));b=formatter.format_run(r);print('文字数',len(b),'/ 通数',len(formatter.split_message(b)))"
```

期待: `文字数 7155 / 通数 2`

**3通以上になったら要注意。** LINEには1実行2通までしか送らないので末尾が切れる。
その場合は `notify_top_n_per_route` を 3 → 2 に下げる。

## T8. Phase 0 — 実際に価格が取れるか（要件2）

**完了条件: 3日連続で成功すること。** 1回成功しただけでは合格にしない。

```powershell
python scripts\phase0_check.py --dest HIJ --save --save-raw
```

- `--save` … 正規化した結果を `tests/fixtures/` に保存
- `--save-raw` … **生HTMLを `tests/fixtures/raw/` に保存**（パーサ回帰テスト用・要件6.2）

### 判定基準

| 確認項目 | OK | NG のとき |
|---|---|---|
| 取得件数 | 1件以上 | ライブラリ/Google側の故障を疑う |
| 航空会社名 | ANA / JAL 等が入っている | `flights_to_flight()` のマッピング調整 |
| 出発・到着時刻 | 両方入っている | 同上 |
| 価格 | **円**の額として妥当 | 通貨が違う。`currency="JPY"` を確認 |

結果を `docs/phase0_log.md` に記録する。翌日・翌々日も同じコマンドで繰り返す。

### 生HTMLを採取したら回帰テストが有効になる

```powershell
pytest tests\test_parser_regression.py -v
```

skip されていたテストが実行されるようになる。以後、Google側の構造が変わると
**このテストが最初に落ちて**気づける。日次実行が失敗し始めたときの切り分けにも使う。

- ここが通るのに本番が失敗 → ネットワーク/Bot判定/一時的な問題
- ここが落ちる → Google側かライブラリ側の構造変化。パーサの修正が必要

### 失敗したら

- `fast-flights がインストールされていません` → `pip install -r requirements.txt`
- `解析に失敗しました` → `artifacts/` に生HTMLが保存されている。それを見て調査
- タイムアウト・接続エラー → ネットワーク。時間をおいて再試行
- 何度やってもダメ → 要件3.2.2 の優先度2（Playwright）へ切替を検討

### 取得できたら実データでドライランする

`config.json` の `fetcher` が `"fast_flights"`、`notifier` が `"console"` であることを
確認して:

```powershell
python -m flightdeal.main
```

LINEには飛ばない。ここで T2 のチェックリストを**実データで**もう一度確認する。

**0件通知でも正常。** ログの `cheapest_total`（実勢の最安）と `market_price`（相場設定）を
比べる。実勢の方が高ければ「お得な便が無い」という正しい判定。
相場設定の見直しは `docs/運用手順.md` を参照。

## T9. Phase 2 — LINEに届くか

### 9-1. 準備

1. [LINE Developers](https://developers.line.biz/) で Messaging API チャネルを作る
2. チャネルアクセストークン（長期）を発行する
3. そのチャネルを自分のLINEで友だち追加する
4. 自分の userId（`U` で始まる文字列）を控える
5. `.env.example` をコピーして `.env` を作り、2つの値を書く

```bat
copy .env.example .env
notepad .env
```

### 9-2. 疎通だけ確認する

**いきなり本番実行しない。** 検索せずテストメッセージだけ送る口がある。

```bat
python -m flightdeal.main --test-notify
```

※ `config.json` の `notifier` を `"line"` にしてから実行する。

期待: LINEに「【テスト送信】…」が届き、`console` ではなく `line への送信に成功しました。`
と表示される。

届かない場合:

| 症状 | 原因 |
|---|---|
| `環境変数が未設定です` | `.env` が読まれていない。値を環境変数に直接 `set` して再試行 |
| `status=401` | トークンが誤り、または失効 |
| `status=400` | userId が誤り |
| 成功と出るが届かない | チャネルを友だち追加していない |

### 9-3. 本番相当で1回流す

`fetcher` を `fast_flights`、`notifier` を `line` にして:

```bat
python -m flightdeal.main
```

**該当便が0件だと何も届かないのが正常**（要件3.6）。
届かないときは `run_no_deal` がログに出ているかを確認する。出ていれば正常。

## T10. GitHub Actions が動くか

1. private リポジトリを作って push する（`.env` が入っていないことを `git status` で確認）
2. Settings → Secrets → Actions に `LINE_CHANNEL_ACCESS_TOKEN` と `LINE_TO_USER_ID` を登録
3. Actions タブ → `daily-flight-check` → **Run workflow**
4. まず `dry_run` に ✅ を入れて実行 → 外部接続なしで環境だけ検証できる
5. 成功したら `dry_run` なしで実行 → 実データ＋LINE通知

期待: 緑になり、Unit tests のステップでテストが全通過する。

その後、3日連続でスケジュール実行（JST 8:00頃）が成功することを確認する。
Actions の cron は数十分遅れることがあるので、8:00ちょうどに来なくても異常ではない。
